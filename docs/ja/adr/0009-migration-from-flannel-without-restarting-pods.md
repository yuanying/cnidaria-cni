# ADR 0009: flannel host-gw からその場で移行し、Pod を再起動しない

- 状態: 決定（2026-09-19）
- 補記の対象: ADR 0005（ipam のストア名をネットワーク名に固定しなくなった）

## 文脈

cnidaria が対象とするクラスターは、いま flannel の `host-gw` バックエンドで動いている。
そのデータプレーンは cnidaria があえて保つ形（ADR 0001）と同じである。ノードごとに
リファレンスの `bridge` プラグインが作る `cni0` という名の Linux bridge が 1 本、アドレスは
`host-local` が配り、相手ノードごとにそのノードのアドレスをネクストホップにした経路が 1 本、
hostPort は `portmap` が担う。flannel の役割は、ノードのサブネットをファイルから読んで
ADD 時に `bridge` + `host-local` の設定を組み立てて委譲する小さな CNI プラグインと、
そのファイルと経路を書くデーモンである。

問うのは、cnidaria が Pod を動かしたままノードを引き継げるか、それとも全 Pod を作り直す
必要があるかである。クラスターの全 Pod を再起動するのは保守停止であり、Pod を残せる
引き継ぎはそうではない。以下がそれを決める部品である。それぞれ、都合のよい想像ではなく
ランタイムとプラグインが実際に何をするかに照らして確かめた。

## 決定

**cnidaria は flannel host-gw のノードをその場で引き継ぐ。動いている Pod はアドレスと
到達性を保つ。** それを成り立たせるもの、そしてそのために設計が約束することは次のとおり。

### 同じ bridge

cnidaria の conflist は bridge を `cni0` と名付ける。これは flannel の委譲設定が既定で作る
名前である。いまある Pod はその bridge に繋がり、ゲートウェイアドレスはそこに付き、
Pod CIDR の connected route はそこを指す。cnidaria の conflist で作られる新しい Pod は同じ
bridge に繋がり、古い Pod を隣人として見る。

別の名前の bridge は選べない。`bridge` プラグインがそれを作り、同じゲートウェイアドレスを
付け、ノードは 1 つのサブネットに 2 つのインターフェースを持つことになる。1 つの prefix に
connected route が 2 本立ち、kernel はパケットごとにどちらかを選ぶ。古い bridge にいる
Pod はゲートウェイを失う。

### 経路は宛先ごとに置き換える

cnidaria が入れる経路はすべて、宛先 prefix をキーにした replace で書く（ADR 0006）。
flannel が入れた相手ノードの Pod CIDR への経路は同じ宛先を持つので、cnidaria の書き込みは
netlink の 1 操作でそれを置き換える。prefix に経路が無い瞬間も、2 本が競合する瞬間も無い。
最初の reconcile が終われば相手ノードへの経路はすべて cnidaria のプロトコル番号を持ち、
以後は ADR 0006 のとおり所有され回収される。引き継ぎより前にクラスターを去ったノードへの
flannel の経路は、計算されないので置き換えられない。cnidaria は自分の印の無い経路を消さない
ので、これは手順書が名指しする残り物になる。

### アドレスのストアは名前で共有する

`host-local` は割り当てを `/var/lib/cni/networks/<名前>` に置く。名前はネットワーク名だが、
ipam ブロックに `name` があればそちらを使う。flannel の conflist の名前は `cbr0` なので、
動いている全 Pod の割り当ては `cbr0` の下にある。cnidaria が自分のストアから割り当てれば、
最初の新しい Pod に、動いている Pod がすでに持つアドレスを渡してしまう。

そこで cnidaria の conflist は、ipam のストアをネットワーク名とは別に名付けられるように
する。デーモンのフラグ `--ipam-store-name` がその名前を ipam ブロックに出し、flannel から
移行するノードは `cbr0` で起動する。既定は空で、host-local は ADR 0005 に書いたとおり
ネットワーク名を使う。ネットワーク名そのものは `cnidaria` のままにする。ランタイムが
自分の帳簿をそれで引くからである。

前の CNI の名前を付けたストアは、そのクラスターでは一時的な設定ではなく恒久的な設定である。
引き継ぎ後に書かれた割り当ても同じディレクトリに入るので、後で名前を変えればそれらが
孤立する。移行が残す目に見える痕跡はこれだけである。

### flannel のプラグインは、その Pod が消えるまで残す

コンテナランタイムは Pod の ADD に使った設定を記録し、DEL はその設定で呼ぶ。DEL の時点で
ディレクトリにある設定ではない。flannel 時代に作られた Pod では、その設定は `flannel`
プラグインを名指ししており、flannel は DEL で `/var/lib/cni/flannel` にコンテナごとに保存した
委譲設定を読み、`bridge` と `host-local` に DEL を渡す。そうした Pod が残っている間に
`flannel` のバイナリやそのディレクトリを消すと、それらの DEL はすべて失敗する。サンドボックスは
それでも壊されるが、割り当ては解放されず、ランタイムは Pod ごとにエラーを記録する。

したがって `/opt/cni/bin/flannel` と `/var/lib/cni/flannel` は、flannel 時代に作られた最後の
Pod が消えるまでそのまま置く。cnidaria はそれを必要ともしないし消しもしない。いつ消せるかは
手順書が言う。

### ランタイムがどの conflist を選ぶか

ランタイムは `/etc/cni/net.d` を読み、名前順で最初のファイルを使う。cnidaria が書く
`10-cnidaria.conflist` は `10-flannel.conflist` より前に並ぶ。デーモンが自分のファイルを
書いた瞬間から、flannel のファイルが残っていようといまいと、新しい Pod はすべて cnidaria の
プラグインで作られる。

cnidaria は `10-flannel.conflist` を消さない。自分が書いていないファイルは何も消さない。
それを消すのは移行手順書の 1 手順である。並び順のおかげでその手順は遅くやっても安全で、
片付け以外には何もそれに依存しない。

### masquerade

flannel の `--ip-masq` による iptables のルールと、cnidaria の `inet cnidaria` の masquerade
（ADR 0003）は同じトラフィックを変換する。ロールアウトの間だけ両方あっても害は無い。
パケットは先に見た側の hook で 1 度だけ変換され、どちらも同じノードアドレスに変換する。
flannel のルールは flannel の DaemonSet と一緒に消える。

## 結果

- 移行は保守停止ではなくロールアウトである。その手順、順序、各手順の確認方法は手順書であり
  この記録ではない。手順書はここの決定に基づいてデプロイの単位が書く。
- ADR 0005 の「ストアのディレクトリは固定のネットワーク名に従う」は補記される。ipam の名前が
  設定されていればストアはそれに従う。ADR 0005 の他の部分はそのまま立つ。
- デーモンのマニフェストは、移行したクラスターでは `--ipam-store-name=cbr0` を載せ、新規の
  クラスターでは省けなければならない。cnidaria で始めたクラスターはこれを設定しない。
- netns テストベッド（ADR 0008）は別の理由でノードごとに ipam のストアを名付けており、
  それによって同じフィールドを実際のプラグインで動かしている。
- 将来 cnidaria を置き換える CNI も、同じ 3 つを保つことになる。bridge の名前、ipam のストア名、
  そして前のプラグインのバイナリをその Pod が消えるまで残すこと。この記録がそのチェックリストである。
