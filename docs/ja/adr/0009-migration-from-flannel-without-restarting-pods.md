# ADR 0009: flannel host-gw からその場で移行し、Pod を再起動しない

- 状態: 決定（2026-09-19）、改訂（2026-09-21、2 回）
- 補記の対象: ADR 0005（ipam のストアを名付けるネットワーク名を設定できるようにした）

## 文脈

cnidaria が対象とするクラスターは、いま flannel の `host-gw` バックエンドで動いている。
そのデータプレーンは cnidaria があえて保つ形（ADR 0001）と同じである。ノードごとに
リファレンスの `bridge` プラグインが作る `cni0` という名の Linux bridge が 1 本、アドレスは
`host-local` が配り、相手ノードごとにそのノードのアドレスをネクストホップにした経路が 1 本、
hostPort は `portmap` が担う。flannel の役割は、ノードのサブネットをファイルから読んで
ADD 時に `bridge` + `host-local` の設定を組み立てて委譲する小さな CNI プラグインと、
そのファイルと経路を書くデーモンである。

問うのは、cnidaria が Pod を動かしたままノードを引き継げるか、それとも全 Pod を作り直す
必要があるかである。クラスターの全 Pod を再起動するのは保守停止であり、Pod を残せる
引き継ぎはそうではない。以下がそれを決める部品である。それぞれ、都合のよい想像ではなく
ランタイムとプラグインが実際に何をするかに照らして確かめた。

## 決定

**cnidaria は flannel host-gw のノードをその場で引き継ぐ。動いている Pod はアドレスと
到達性を保つ。** それを成り立たせるもの、そしてそのために設計が約束することは次のとおり。

### 同じ bridge

cnidaria の conflist は bridge を `cni0` と名付ける。これは flannel の委譲設定が既定で作る
名前である。いまある Pod はその bridge に繋がり、ゲートウェイアドレスはそこに付き、
Pod CIDR の connected route はそこを指す。cnidaria の conflist で作られる新しい Pod は同じ
bridge に繋がり、古い Pod を隣人として見る。

別の名前の bridge は選べない。`bridge` プラグインがそれを作り、同じゲートウェイアドレスを
付け、ノードは 1 つのサブネットに 2 つのインターフェースを持つことになる。1 つの prefix に
connected route が 2 本立ち、kernel はパケットごとにどちらかを選ぶ。古い bridge にいる
Pod はゲートウェイを失う。

### 経路は宛先ごとに置き換える

cnidaria が入れる経路はすべて、宛先 prefix をキーにした replace で書く（ADR 0006）。
flannel が入れた相手ノードの Pod CIDR への経路は同じ宛先を持つので、cnidaria の書き込みは
netlink の 1 操作でそれを置き換える。prefix に経路が無い瞬間も、2 本が競合する瞬間も無い。
最初の reconcile が終われば相手ノードへの経路はすべて cnidaria のプロトコル番号を持ち、
以後は ADR 0006 のとおり所有され回収される。引き継ぎより前にクラスターを去ったノードへの
flannel の経路は、計算されないので置き換えられない。cnidaria は自分の印の無い経路を消さない
ので、これは手順書が名指しする残り物になる。

### アドレスのストアはネットワーク名で共有する

`host-local` は割り当てを `/var/lib/cni/networks/<ネットワーク名>` に置く。ipam ブロックにも
`name` というフィールドはあるが、host-local はストアを開く前にそれをネットワーク名で
上書きするので、ディレクトリを決めるのはネットワーク名だけである。flannel の conflist の
名前は `cbr0` なので、動いている全 Pod の割り当ては `cbr0` の下にある。cnidaria が自分の
ストアから割り当てれば、最初の新しい Pod に、動いている Pod がすでに持つアドレスを渡して
しまう。

そこで cnidaria のネットワーク名は設定できるようにする。デーモンのフラグ `--network-name`
で、既定は `cnidaria`。flannel から移行するノードは `cbr0` で起動する。名前が何であれ、
bridge をはじめ conflist の他の部分は同じである。

前の CNI の名前を付けたネットワークは、そのクラスターでは一時的な設定ではなく恒久的な設定である。
引き継ぎ後に書かれた割り当ても同じディレクトリに入るので、後で名前を変えればそれらが
孤立する。移行が残す目に見える痕跡はこれだけである。

### 前の CNI の設定は cnidaria が来る前に退かす

コンテナランタイムが `/etc/cni/net.d` の先頭のファイルだけを使うとは限らない。containerd は
`max_conf_num` の設定が許す数だけ読み込み、2 つ以上読み込んでいれば、新しい Pod はその
すべてに接続される。インターフェースが 2 つ、アドレスが 2 組、default 経路が 2 本になる。
`10-cnidaria.conflist` と `10-flannel.conflist` が並んでいる間に作られた Pod は、両方に
接続されてしまう。

そこで移行は、cnidaria がディレクトリに書く前に前の CNI をそこから退かす。順序は、
flannel の DaemonSet を消して誰もその conflist を書き直さないようにし、全ノードの
`10-flannel.conflist` を消し、それから cnidaria をデプロイする。その間、動いている Pod には
何も起きない。bridge もアドレスも経路も kernel にそのまま残っている。conflist が 1 つも
無い間に作られた Pod は、ランタイムがネットワーク未準備と報告するので `ContainerCreating`
で待ち、cnidaria がファイルを書いた時点で作られる。

cnidaria は `10-flannel.conflist` を消さない。自分が書いていないファイルは何も消さない。
それを消すのは移行の 1 手順であり、オペレーターが行う。

### flannel 時代の Pod は cnidaria の conflist で消される

containerd は DEL を、その Pod の ADD に使った設定ではなく、DEL の時点でディレクトリに
ある設定で呼ぶ。flannel 時代に作られた Pod は、したがって cnidaria の `bridge` と
`host-local` で片付けられる。これが成り立つのはネットワーク名が同じだからである（前述）。
host-local は共有したストアの中でそのコンテナ ID の割り当てを見つけて解放し、`bridge` は
同じ `cni0` から Pod の veth を外す。

`/opt/cni/bin` の flannel のバイナリと `/var/lib/cni/flannel` の状態は、以後読まれない。
残しておいても害は無く、cnidaria はそれを消さない。

### masquerade

flannel の `--ip-masq` による iptables のルールと、cnidaria の `inet cnidaria` の masquerade
（ADR 0003）は同じトラフィックを変換する。両方あっても害は無い。パケットは先に見た側の
hook で 1 度だけ変換され、どちらも同じノードアドレスに変換する。flannel は DaemonSet を
消してもルールをすべて消すわけではなく、IPv6 のルールが残ることが観測されている。
それは手で、急がずに消す。

## 結果

- 移行は保守停止ではなくロールアウトである。その手順、順序、各手順の確認方法は手順書であり
  この記録ではない。手順書はここの決定に基づいてデプロイの単位が書く。
- ADR 0005 の「ネットワーク名は固定」は補記される。デーモンに別の指定が無ければ `cnidaria`
  である。ADR 0005 の他の部分はそのまま立つ。
- デーモンのマニフェストは、移行したクラスターでは `--network-name=cbr0` を載せ、新規の
  クラスターでは省けなければならない。cnidaria で始めたクラスターはこれを設定しない。
- netns テストベッド（ADR 0008）は別の理由でノードごとにネットワークを名付けており、
  それによって同じストアの名付けを実際のプラグインで動かしている。
- ノードで flannel の conflist が消えてから cnidaria の conflist が来るまでの間、新しい Pod は
  作れない。その間はロールアウトの速さの分だけ続き、動いているものには影響しない。
- 将来 cnidaria を置き換える CNI も、同じものを保つことになる。bridge の名前、ネットワーク名、
  そして自分の conflist を置く前に cnidaria の conflist をディレクトリから退かすこと。この記録が
  そのチェックリストである。

## 改訂

**2026-09-21、動いているクラスターで移行を試したとき。** 最初の版は、ipam ブロック自身の
`name` が host-local のストアを選ぶとし、ネットワーク名は `cnidaria` のまま前の CNI の名前を
そこに出す `--ipam-store-name` フラグを足していた。host-local はそのフィールドを使わず、
ネットワーク名で置き換える。フラグは何も変えず、ストアは新しいものになっていた。フラグは
廃止した。設定するのはネットワーク名（`--network-name`）になり、host-local が実際に読むのは
それである。アドレスのストアの節はそのように書き直した。

**2026-09-21、同じ移行で。** ランタイムと flannel についての 3 つの記述が誤っていた。
それに依っていた節は書き直した。

- 「ランタイムは名前順で最初のファイルを使う」。containerd は `max_conf_num` まで読み込み、
  読み込んだすべてのネットワークに Pod を接続する。cnidaria のファイルが先に並ぶことで、
  flannel のファイルを消すのは後回しにできる片付けになるはずだったが、そうはならない。
  移行は、cnidaria をデプロイする前に前の CNI の設定を退かすようにした。
- 「ランタイムは ADD に使った設定で DEL を呼ぶ」。containerd は DEL の時点にある設定を使う。
  flannel のバイナリと状態をその Pod が消えるまで残すのはこの記述からの帰結だったが、
  もう要らない。古い Pod の割り当てを解放するのは、共有したネットワーク名である。
- 「flannel の masquerade のルールは DaemonSet と一緒に消える」。IPv6 のルールは残った。
  害は無く、手で消す。
