# ADR 0005: アドレス割り当ては host-local に任せ、`node.spec.podCIDRs` から与える

- 状態: 決定（2026-09-19）
- 補記: ADR 0009（2026-09-19）— ipam の名前が設定されていればストアのディレクトリはそれに従う。
  別の CNI から移行するノードがその割り当てを共有するため

## 背景

各 Pod は、ノードの 2 つの `podCIDRs` から IPv4 と IPv6 のアドレスを 1 つずつ必要とする。
割り当ては、デーモンの再起動やノードの再起動をまたいでも、まだ使われているアドレスを
配り直すことなく生き残らなければならない。`podCIDRs` は Node が参加したときに
controller manager が割り当て、その後変わることはないので、範囲は固定の入力である。
決めるべきは、リースの状態を誰が持つかである。

選択肢は、デーモン内部のアロケータ（コンテナランタイムがアドレスをデーモンに問い合わせる
必要が生じ、それは自前のプラグインを意味する —— ADR 0001 で退けている）、自前プラグイン
内部のアロケータ（同上）、そしてリファレンスプラグインの `host-local` であった。

## 決定

**IPAM は `host-local` に委譲する。** cnidaria はアロケータを書かない。

- conflist の `bridge` エントリは IPAM として `host-local` を指名し、アドレスファミリ
  ごとに 1 つの範囲セットを持ち、各セットにそのファミリの `podCIDR` を入れる。host-local は
  各セットから 1 つずつアドレスを割り当てる。これが Pod にファミリごとに 1 つのアドレスを
  与える仕組みである。
- `host-local` は各範囲の先頭アドレスをゲートウェイ用に予約する。これは `isDefaultGateway`
  が設定されたとき `bridge` が `cni0` に付けるアドレスである。cnidaria の中でゲートウェイ
  アドレスを知る必要があるものは無い。
- リースの状態は host-local のファイルストア、すなわちノード上の
  `/var/lib/cni/networks/<ネットワーク名>` が持つ。割り当てたアドレスごとに 1 ファイルで、
  中身はコンテナ ID である。デーモンの再起動でもノードの再起動でも残る。DaemonSet は
  そのために何もマウントしない。プラグインは Pod の中ではなくホストで動くからである。
- conflist のネットワーク名は固定（`cnidaria`）なので、ストアのディレクトリは安定し、
  conflist を書き直してもリースが孤立することはない。

## 帰結

- 入力は `podCIDRs` だけである。controller manager が IPv4 しか割り当てないクラスターでは
  Pod も conflist も IPv4 のみになる。レンダラーは同じファミリのプレフィックスが 2 つある
  場合を拒否する。host-local のゲートウェイの慣習はファミリごとに 1 つの範囲セットを
  前提としているからである。
- `DEL` が届かなかった Pod（sandbox の破棄と CNI 呼び出しの間でランタイムがクラッシュした
  場合）は、何かが回収するまで古いリースファイルを残す。リファレンスプラグインはこのために
  CNI 1.1 の `GC` 動詞を実装しているが、使用中のコンテナランタイムはまだこれを呼ばない。
  これは flannel ベースのノードと同じ挙動であり、上限もある。失われた `DEL` 1 つにつき
  アドレス 1 つで、数十の Pod を動かすノードの `/24` には余裕がある。問題になるようなら、
  デーモンが生きている Pod sandbox ID の一覧を渡して `GC` を呼ぶことができる。それは後の
  ADR の話である。
- Node の `podCIDRs` を変えることは Kubernetes がサポートしておらず、この設計でもサポート
  しない。範囲を移さなければならないノードは drain し、削除して、再参加させる。これで
  リースストアも消える。
