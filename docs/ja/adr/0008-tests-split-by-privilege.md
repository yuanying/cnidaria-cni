# ADR 0008: テストは必要な権限で分け、権限が要るものはコンテナで回す

- 状態: 決定（2026-09-19）

## 背景

cnidaria がすることの大半はカーネル無しで検査できる。conflist のレンダリング、
NetworkPolicy オブジェクトからチェーンモデルへの変換、そのモデルから nft テキストへの
レンダリング、経路の選択。できないものもある。パケットが実際に bridge と経路とルールセット
を通って Pod から Pod へ届くか、ポリシーが落とすと言っているものを実際に落とすか。それらには
root、`CAP_NET_ADMIN`、ネットワーク名前空間、そして `nft` と `ip` のコマンドが要る。

同じテストを、`nft` が無く、何も入れてはいけないマシンでも回せなければならない。だから
ツールはテストと一緒に運ぶ。regied も同じ制約に直面し、
[ADR 0010](https://github.com/yuanying/regied/blob/main/docs/adr/0010-netns-testbed.md)
で決着をつけた。この記録はその答えを採用し、cnidaria のテストベッドが違うところを記す。

## 決定

### build tag で分けた 2 つの層

| 層 | コマンド | 必要なもの | 含むもの |
|---|---|---|---|
| unit | `make test` | Go ツールチェイン | 固定の入力に対する純粋関数。レンダラー（golden ファイル）、意味論（ケースの表）、fake オブジェクトに対する reconcile ロジック |
| netns | `make test-netns` または `make test-netns-docker` | root、`nft`、`ip` | ネットワーク名前空間で組んだ「ノード」を外側から動かす |

netns テストは build tag `netns` の後ろにあり、`go test ./...` が拾うことはない。tag 付きの
ファイルが腐らないよう、`go vet` と linter も tag を付けて走らせる。

ノードと Pod のテストベッドは `test/netns` にある。新しい名前空間 1 つと `nft` だけで済む
tag 付きテスト（描画したテーブルが受理される、再適用で何も変わらない、他のテーブルが
適用後も残る）は、検証対象のパッケージの隣、`internal/nftables` に置き、make ターゲットは
モジュール全体に tag を付けて走らせる。

### netns スイートは、走れないときに大きな声で失敗する

このスイートを求めることは、ツールがあるはずだという表明である。make ターゲットと
コンテナイメージは `CNIDARIA_NETNS_REQUIRE=1` を設定し、この下ではツールの欠如や root で
ないプロセスは、skip ではなく理由付きの失敗になる。`go test` は skip メッセージしか出さな
かったパッケージにも `ok` と印字するので、実際には走らなかった実行が緑に読めてはなら
ない。この変数無しの素の `go test -tags netns` は、手元で試す人のために skip のままである。

### 特権付きの兄弟コンテナで回す

`make test-netns-docker` は `nft`、`ip`、Go ツールチェインを入れたイメージをビルドし、
リポジトリを同じパスにバインドマウントして `--privileged` で起動し、その中で
`make test-netns` を実行する。ホストには何も入れない。Go のビルドキャッシュとモジュール
キャッシュは実行したユーザーのキャッシュディレクトリからマウントし、実行のたびに標準ライブラリを
ビルドし直さないようにする。

### テストベッドとは何か

各「ノード」は、bridge と、L2 ネットワークの代わりを務める共有の「セグメント」名前空間へ
の veth ペアと、実ノードと同じ sysctl（ADR 0002）を持つネットワーク名前空間である。Pod は
さらに別の名前空間で、実物の conflist（ADR 0001）で駆動した実物のリファレンスプラグインを
通して bridge に接続する。テストは代役ではなくプラグインそのものを動かす。アドレスは文書用
の範囲（RFC 5737、RFC 3849）から取る。

検証は Pod とノードの名前空間から行い、被試験対象のテーブルを読むことでは行わない。ルール
セットを覗くテストは 1 つのレンダリングにしか当てはまらないが、パケットを送るテストは
どれにでも当てはまる。区別が要るところでは、regied のテストベッドと同じく「落とされた」と
「誰も聞いていない」を時間で見分ける。

最初の作業単位ではデーモンはループの中にいない。テストは unit テスト済みのレンダラーが
出した経路とルールセットを適用する。デーモン自体を名前空間に入れて fake の API サーバーに
向けるのは後の追加であり、この構成を変えるものではない。

## 帰結

- 骨組みの段階ではテスト 0 件のハーネスを出荷し、`make test-netns-docker` は「走らせる
  テストが無い」と報告することでハーネスが端から端まで動くことを示す。各実装単位が自分の
  テストを足す。
- CI は unit の層だけを回す。netns の層は開発者のマシンか特権コンテナを許すランナーで回し、
  タスクの完了条件はそれを明示的に挙げている。
- 開発ホストとノード（arm64 のベンダーカーネル）とのカーネル差はここでは扱わない。netns の
  層はクラスターの前の関門であって、代わりではない。
