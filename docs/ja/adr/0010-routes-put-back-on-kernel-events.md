# ADR 0010: 経路が消えたとカーネルが知らせたら入れ直す

- 状態: 決定（2026-10-17）

## 背景

ADR 0006 では、デーモンの与り知らぬところで消された経路は次の reconcile が戻す。
reconcile は Node のイベントごとと、タイマーで走る。経路が消えても Node オブジェクトは
何も変わらないので、実際に戻すのはタイマーであり、その間隔は 5 分である。それまでの間、
そのノードと相手ノードの間では、そのファミリの Pod 同士が通信できない。

経路がまとめて消えるのは、運用者の誤操作ではなく普通に起きることである。アップリンクを
管理し、自分が作っていない経路も管理するよう設定されたネットワークマネージャー
（systemd-networkd は既定でそうする。`ManageForeignRoutes=yes`）は、再起動のときにそれらを
すべて消す。再起動は、パッケージの更新、プロビジョニングツールの再実行、自動更新で起きる。
インターフェースが落ちて上がったときや、アドレスが外れて付け直されたときも、経路は道連れに
なる。

これらについてカーネルが netlink の購読者に何を知らせるかは、ファミリによって違う。
ネットワーク名前空間で確かめた結果は次のとおり。

- 明示的に消された経路は、ネットワークマネージャーや運用者が消す場合を含め、両ファミリとも
  通知される。
- インターフェースが落ちて消えた IPv6 の経路は通知される。
- インターフェースが落ちて、またはゲートウェイを on-link にしていたアドレスが外れて消えた
  IPv4 の経路は、**通知されない**。経路はただ無くなる。

したがって経路の削除だけを見ていれば、ネットワークマネージャーの場合は拾えるが、それ以外の
場合の IPv4 は黙ったままになる。

## 決定

デーモンは、経路を入れる名前空間で、カーネルの経路・リンク・アドレスの通知を netlink で
購読し、次のどれかが通知されたら経路の reconciler に実行を頼む。

- **自分の経路が消された** ―― cnidaria の protocol の印（ADR 0006）を持つ経路。ファミリは
  問わない。他人の経路が消えたことは理由にしない
- **リンクが up でキャリアがある** ―― リンクの道連れになった IPv4 の経路を、また入れられる
  ようになる時点
- **global スコープのアドレスが付いた** ―― アドレスと一緒にゲートウェイに届かなくなった
  IPv4 の経路を、また入れられるようになる時点。リンクローカルのアドレスは数えない。新しい
  Pod のインターフェースはどれもそれを持つ

購読は、聞き始めた時点でも 1 回の実行を頼む。それ以前に起きたことのためである。読み解けな
かった通知も実行を頼む。数えるべき通知だったかもしれないからである。

これらは Node のイベントと同じ、ワークキューの 1 つのキーに入る。reconcile は実行時点の
テーブルを読むので、通知がまとまって来ても待っている実行は 1 つで足り、残りは捨てる。
reconcile は従来と同じ全体の再計算と適用なので、経路を変える道筋が 2 つになることはない。
自分の変更でループもしない。自分の古い経路を消すと実行がちょうど 1 回増え、その回は何も
することがない。経路・リンク・アドレスの追加や置き換えは理由にならない。

ADR 0006 のタイマーの reconcile は、同じ間隔で残す。これからは、すべての消失ではなく、
何も通知されない消失 ―― リンクが上がったまま IPv4 の経路が消え、アドレスも戻らない場合
など ―― の上限になる。

テーブルにそのネクストホップで無かった経路を入れたときは、ノード名と一緒にログに出す。
戻した経路が跡を残すようにするためである。すべて揃っていた reconcile は経路について何も
出さない。

購読が止まった場合 ―― ソケットが失敗した場合で、溢れて通知が失われたときもそうなる ――
watch はエラーで終わり、Manager も一緒に終わるので、デーモンは DaemonSet によって再起動
される。watch 無しで動き続けるデーモンは、健全に見えながら 5 分待ちに戻ってしまう。
再起動は、入っている経路には触らない。

### 検討した別案

- **タイマーを短くするだけ。** 単純だが、待ち時間は結局その間隔であり、秒単位にすると、
  年に数回の出来事のために全ノードで数秒ごとに経路と iptables のチェインを適用し直すことに
  なる。
- **経路の削除だけを見る。** 実際に起きたネットワークマネージャーの再起動は拾えるが、
  リンクの上下で消えた IPv4 の経路はタイマー待ちのままになる。リンクとアドレスの通知で、
  わずかなコストでこれを塞げる。
- **リンクとアドレスの通知をすべて拾う。** Pod の作成と削除で Pod ごとに複数来る。上の
  条件は、消えた経路が戻せるようになる通知だけを残す。
- **ネットワークマネージャーに他人の経路を放っておかせる。** ネットワークマネージャーが
  動くノードでは正しいが、デーモンからは見えず強制もできないノードの設定であり、経路が
  消える他の道筋も残る。

## 結果

- ネットワークマネージャーの再起動の後、経路は resync の間隔までではなく、reconcile 1 回
  ぶんの時間で戻る。
- デーモンは netlink のソケットを 3 つ余分に持つ。Pod のインターフェースが上がることも
  リンクが上がることに数えるので、ノードで Pod が出入りすると経路の reconciler が少し多く
  走る。何も変えない reconcile のコストは、キャッシュの読み出し、相手とファミリごとの
  経路の置き換え、iptables のチェインの確認である。
- カーネルの watch に要る権限は、経路を入れるのに要る権限（ホストのネットワーク名前空間での
  `CAP_NET_ADMIN`）を超えない。
- netns のテストベッド（ADR 0008）で確かめる。1 つのノードで watch を動かした状態で、
  そのノードの経路を消すと、またアップリンクを落として上げてアドレスを付け直すと、どちらでも
  経路と Pod 同士の到達性が数秒のうちに戻る。
