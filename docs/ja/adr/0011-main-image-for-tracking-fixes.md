# ADR 0011: main の先頭を :main として公開する

- 状態: 決定（2026-10-27）

## 背景

これまでイメージを公開していたのは、リリースのタグ（`vX.Y.Z`）と、人が手で公開するブランチだけ
だった。cnidaria-cni を動かすクラスターでは、そのイメージの脆弱性をスキャンできる。修正版のある
検出は、クラスターから消えるまでに段階を踏む。依存やベースイメージを main で上げ、リリースのタグを
打ち、デプロイが新しいタグを取り込み、それを適用する。

これらの段階を見分けるには、main がすでに修正を含んでいるかをスキャナーが知る必要がある。
main の `go.mod` や Dockerfile を読むだけでは足りない。検出はベースイメージのパッケージにあることが
多く、イメージが結局何を含むかは、main からビルドしたイメージをスキャンして初めて分かる。
そのイメージは、コミットを知らなくてもスキャナーが見つけられる名前で公開し、どのコミットから
ビルドしたかを示す必要がある。

push のたびにイメージを公開すると、前のものがレジストリに残る。ghcr.io ではタグを動かすと古い
イメージが untagged の版として残り、積み上がる。マルチアーキのイメージでは、この掃除が繊細になる。
タグが付くのは index で、index が指すプラットフォームごとの manifest と attestation は、タグの
見えない別の版である。タグの無い版をすべて消すと、タグ付きのイメージが壊れる。

## 決定

- **main への push のたびに、イメージを `ghcr.io/yuanying/cnidaria-cni:main` として公開する。**
  その push で CI ワークフローの検査が通ってからである。タグは `main` で、push のたびに動く。
  コミットごとのタグは出さない。イメージはリリースと同じワークフロー、同じ `make image` で
  ビルドするので、アーキテクチャ（`linux/amd64`、`linux/arm64`）とラベルはリリースと同じになる。
  溜まった push は順に 1 つずつ公開し、古いコミットが新しいものを上書きしないようにする。
- **すべてのイメージの config に OCI のラベルを 2 つ付ける。** `make image` が付ける。
  `org.opencontainers.image.source` はリポジトリの URL、`org.opencontainers.image.revision` は
  ビルド元のコミットの full SHA。リリースにも付ける。スキャナーは前者でイメージのソースを見つけ、
  後者をリリースのコミットと比べて「main で直ったが未リリース」と「リリースで直った」を見分ける。
- **`:main` を公開するたびに、untagged の版を消す。** `dataaxiom/ghcr-cleanup-action` の
  `delete-untagged` を使う。この Action はタグ付きの index をたどり、それが指すプラットフォームの
  manifest と attestation を残すので、リリースでも `:main` でも、タグ付きのイメージは壊れない。
  1 時間より新しい版は対象から外す。進行中の push のプラットフォームの manifest は、まだどの
  index からも指されていないので、それを消さないためである。この Action はパッケージの版を消す
  権限を持つので、commit SHA で pin する。
- 掃除は dry-run から始めず、最初から実際に消す。この Action はタグ付きの index の子を残すことを
  前提に作られている。消した版は id がログに残り、30 日のあいだ GitHub の API で戻せる。

## 結果

- リリースは変わらない。手で push したタグも週次のリリースも、これまでどおりバージョンのタグで
  公開する。ラベルが 2 つ付くようになる。
- `:main` はリリースではなく、デプロイに使うものではない。スキャンのためにある。ただしリリースと
  同じビルドを通るので、main でビルドが壊れればその push で分かる。次のリリースを待たない。
- パッケージに残るのは、リリースのタグと `:main` である。掃除が走ったときに 1 時間未満だった
  前の `:main` は、次の push の後の掃除まで残る。容量はリリースの数に応じて増え、push の数には
  比例しない。
- 掃除には、ワークフローのトークンがパッケージの Admin ロールを持つ必要がある。このリポジトリの
  ワークフローが最初に公開したパッケージならそうなっている。別の経路で作られたパッケージなら、
  パッケージの「Manage Actions access」でロールを与える。
- 消すべきでないものを消すと分かったときは、消したものがジョブのログにあり、戻せる。原因を
  調べるあいだは、Action の `dry-run` を有効にして止める。
